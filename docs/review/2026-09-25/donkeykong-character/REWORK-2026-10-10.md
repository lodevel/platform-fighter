# Donkey Kong art rework (decided 2026-10-10)

User decisions (2026-10-10):

- **Art is reworked from zero, Pikachu-style.** The existing 256 px flat-red sprites and
  the per-drawing repair chain under `audit-2026-10-08/art` are retired as the production
  path (kept as evidence). Mechanics stay: sourced frame data, damage/launch, hitbox
  timelines, grab/throw logic, the 226-row `inventory.json`.
- **Appearance: classic DK.** Brown fur, tan face/chest/hands/feet, red tie with yellow
  "DK" letters, unarmed, clean 2D cartoon with Pikachu's resolution and line quality.
- **Transition: swap per family.** Old sprites stay in the game until a family's new art is
  accepted and checked in a match; DK stays playable throughout.
- **Acceptance bar = Pikachu's.** Rough-beta pose acceptance by actual inspection (identity,
  limb count, connected alpha, nothing changed outside the mask, root/foot registration),
  flaws recorded rather than repaired pixel by pixel; then per-action match evidence.
- **Image retry budget: 5 generation attempts per pose.**

## Why

Side-by-side at native resolution, Pikachu's 512 px cells have clean outlines and shading;
DK's 256 px cells are blocky, flat and off-model. The previous DK pose path traced edges
from the *textured* fur render, giving noisy guides and grainy flat outputs that were then
repaired hand by hand (two dash-grab drawings took most of a day). Pikachu used one generic
recipe for ~426 GPU jobs in ~43 h with ~1 attempt per pose.

## Pipeline (copied from Pikachu, `docs/review/2026-10-06/pikachu-character/art/README.md`)

1. Native DK model posed per source sample (`tools/dk_native_pose.py`, `tools/dk-native-guide.py`).
2. **New for DK:** guide + seed rendered by *material*, not texture: flat fur/skin/tie/eye
   colours sampled from the accepted reference; guide lines only from silhouette,
   occlusion/depth jumps and material borders (no fur-texture edges).
3. Masked img2img: colored seed -> VAEEncode -> SetLatentNoiseMask, Fun ControlNet Union on
   the guide, Z-Image Turbo int8, 8 steps, cfg 1, denoise 0.65, ImageCompositeMasked.
4. Tiled 2x2 atlas of 1024 px cells per job, one fixed seed, one job at a time, immutable ledger.
5. Fixed root and one uniform world scale; pack to 512 px cells with per-animation metadata.
6. Re-fit receiving geometry to the new body; per-family swap and match verification;
   Pikachu regression each swap.

Phases: 0 identity reference -> 1 pilot (idle, jab 1/2, one smash) -> 2 family batches ->
3 per-family install + match evidence. Progress is tracked in `inventory.json`
(`active_work.rework_2026_10_10`).

## Swap recipe (runtime map, 2026-10-10)

Preload reads per-clip `frameWidth/frameHeight/frameCount` generically (`src/assets/manifest.ts`),
so 512 px cells need no loader change. For each swapped clip:

1. Replace `assets/characters/donkeykong/animations/<clip>.png`; update its `frames.json` entry
   (`frameWidth`, `frameHeight`, `frameCount`, `sourceCells`, `columns/rows` if atlas-packed).
2. Add `root`, `scaleToWorld`, `bodyCentreFromRootY`. `getDonkeyKongBodyRenderMetrics`
   (`src/characters/donkeykongBodyPresentation.ts`) gates on `root && scaleToWorld` only, and
   MatchScene then renders that clip with per-clip metrics instead of the DK-global
   `visualScale.ts` calibration (224 / 16/256), which stays for unconverted clips.
3. Generic-path clips (idle, run, jump, crouch, shield, hurt, aerials, ...) carry no
   `frameWindows`: the body-default hurtbox applies and no receiving geometry is required.
4. Clips with `frameWindows` (jab, jab2, dtilt, grab, grab_pull, grab_hold) require
   `hurtboxPoses` for every art frame (and attack/catch/grip poses where present) or
   `getDonkeyKongBodyDrawing` throws; these are re-fitted to the new drawings.
5. Hand/item anchors are a static per-fighter table (`src/characters/handAnchors.ts`); re-measure
   once against the new body.

Guarding tests: `src/assets/manifest.test.ts`, `src/characters/spriteAnimationDriver{,.sheets}.test.ts`,
`src/characters/simulationSpriteAnimation.test.ts`, `src/characters/simulationStandingGrabFallback.test.ts`,
`src/characters/DonkeyKong.test.ts`, `src/characters/donkeykongCompleteGrab.test.ts`,
`src/characters/donkeykongPairedActionTimeline.test.ts`, `src/characters/donkeykongCatchCollisionPose.physics.test.ts`,
`src/characters/characterSpec.test.ts`, `src/characters/donkeykongMovementRuntime.test.ts`,
`src/characters/DonkeyKong.collisionGeometry.test.ts`. No test guards DK render metrics directly: add one with the first swap.

`pikachuPresentation.ts` and `donkeykongBodyPresentation.ts`.

## Scale contract (2026-10-10)

Relative fighter size follows the native models: **5 world units per native unit**, the same
as Pikachu (`ART_PIXELS_PER_UNIT = 5/(70/600)` in `tools/pikachu-native-guide.py`, ~14 native
units tall = 70 world) and the old DK (26 px/unit, `scaleToWorld` 5/26). Art may be rendered at
any resolution (idle normalized to ~600 px for detail), but each render records
`art_pixels_per_native_unit` (ppu) and the packed clip uses world-per-art-pixel = 5/ppu,
never Pikachu's 70/600. DK should therefore read roughly twice Pikachu's height in a match.
User delegated fighter size decisions to the coordinator (2026-10-10): keep the native-model
ratio by default; revisit only after seeing DK in a match (option: centralize DK's scattered
`* 5` native-to-world factor into one per-fighter size constant).
