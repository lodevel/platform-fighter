# Link Ultimate rebuild: runtime audit and integration plan

This is a fresh implementation from new source contracts and a new reference,
with every animation regenerated. The previous Link class and evidence serve
as an integration map and revision-checked research only. No row begins visually
or behaviorally qualified. See `runtime-plan.json` for file ownership, source
requests, shared consumers, item rows, migration decisions and ordered gates.

The audit was read-only outside these planning documents. No production source,
data, assets, active roster, tests or current DK/Pikachu records were changed.
No tests, typecheck, browser, build or probes ran. Implementation stays behind
the coordinator's current DK/Pikachu exact-build publication gate. The user
requests one complete Link verification at the end.

## Existing integration map and concrete gaps

`Link.ts` is already registered, but `activeFighters.ts` still lists only DK and
Pikachu. It registers20 intrinsic attack exports and Grab through ContractFighter.
The canonical authorable registry derives compiled slots from stable `LINK_*`
exports; replacing that public surface accidentally would lose Lab slots.
Existing IDs include `link.utilt`, `link.usmash`, `link.dtilt`, `link.dsmash` and
snake-case special IDs; these require explicit source mapping before any rename.

Current normals mix sourced packets and approximate collision. Jab3 explicitly
omits the animated sword-bone hitbox; dash attack approximates spatial variants.
Bow/boomerang/spin/bomb use generic projectile, boomerang, rising multihit and
trap schemas. The aerial spin admits approximate autolink/target-position
behavior, and many projectile/kinetic values are calibrated. Getup and ledge
attacks are generic authored subclass overrides rather than complete contextual
source declarations. These are named missing rebuild rows, not acceptable
defaults for a full Ultimate Link.

The factory registers saved custom moves, but special execution hooks consult
compiled moveset IDs. New special/resource contracts must survive serialization,
reload, overridden IDs, Lab and Test Fight rather than work only in BASE.
Shared serializers have extensive schema support; that does not prove all
required Link resource/state fields exist or reach consumers.

All16 supported catalog items need Link-specific compatibility. Current item
profiles cover only DK/Pikachu and silently default others to DK; heavy admission
gates cover those two fighters; independent socket/axes tables omit Link;
layered shooting waist registration is Pikachu-only. Link's static(25,-6) hand
fallback and legacy strips cannot qualify grips, moving composition or native
callbacks. RemoteBombAdapter also uses the static hand helper, independently
of current drawn equipment registration.

The source agent has now confirmed mandatory passive shield blocking during
idle/walk/crouch with SDI, picked-up arrow double-shot and +3-frame timing,
full-health swordbeam, down-air pogo, Boomerang ordinary/smash/return/catch/blank
states and Remote Bomb ownership branches. These require real consumers rather
than optional fallback clips. New reference keeps the current green outfit/palette
identity through fresh generation, with Ultimate right-handed sword/left shield.
Entry/respawn and victory presentation follow the actual menu/match/results
consumers. The user subsequently explicitly included all three Ultimate Finals
and the shared Final Smash system; the former scope exclusion is superseded. Swimming/
ladder have no mapped stage/input runtime in the bounded audit; missing engine
support must be recorded distinctly from source non-applicability.

Legacy visualScale notes explicitly describe inconsistent generated Link facing.
New reference roots/scale, anatomical foot support, grips/muzzles and receiving
poses must replace those assumptions together. Sword, Hylian Shield, bow,
boomerang and bomb equipment state must follow native source conditions per
move rather than be merely painted onto an animation.

## Ownership and shared boundaries

The runtime owner owns replacement `src/characters/Link.ts` and the planned
Link-specific move data, movement, special/article, body/auxiliary receiving,
equipment and item/heavy helpers listed in the JSON. Those helper names reserve
the partition; source contracts may consolidate it without treating scaffolding
as implementation. Source agent owns canonical inventory/captured contracts;
Golden owns new reference, every animation and independent registration metadata.

The coordinator arbitrates shared Character/MatchScene hooks, item definitions
and profiles, serializer/factory, movement registry, animation registration,
socket/layer consumers, manifest, masks, capture/AI and snapshot changes before
edits. No specialist duplicates ownership of those files. Shared extensions
must retain current DK/Pikachu behavior and user choices: readable charge/load
status, immediate new-shot facing, proper moving shooter joins, pass-through
item landing, F3-only diagnostics and removed decorative attack rings.

Mechanics/equipment contracts are requested for every contextual action,
including source spin ground/air motion, charge/cancels, projectile reflection/
absorption, arrow landing/pickup/double-arrow branches where applicable,
boomerang aiming/return/catch, bomb ownership/physics/detonation, conditional
swordbeam and passive shield. Applicability and numeric rules come from the
new source inventory, not the names of old schemas. Required missing native
flags, clock semantics and shared behavior stay explicit until their consumers
are wired and final match acceptance observes them.

## Compatibility and final acceptance

Keep semantically matching public exports and move IDs; introduce explicit IDs
for newly distinguished branches. Preserve old saved tunes and their authored
numbers. A versioned baseline/schema migration or explicit legacy branch is
needed where new resource contracts cannot safely infer old fields; old records
must not be silently overwritten with new BASE behavior. Old replay files and
evidence remain preserved, with changed engine/build identity distinguished
from deterministic reproduction of historical gameplay.

Enable Link alongside DK/Pikachu only when new reference/baselines and all
applicable runtime/art rows are ready. Final verification runs after the complete
freeze: schemas/typecheck and relevant source/physics tests, actual movement,
contact/hit/miss/protection/resource/interruption boundaries, save/load/Lab/Test
Fight, exact-build normal-input match checks for every action and item, and
shared-change regressions. A later correction inside that final verification
cycle must rerun its affected checks; it does not authorize per-edit check loops
during implementation. Full completion requires accepted visuals and observed
match behavior for every applicable row, with source gaps/calibrations stated.

## Shared Final Smash system and three Ultimate Finals

Required scope now includes DK Jungle Rush, Pikachu's automated Volt Tackle and
Link Ancient Bow and Arrow. Ordinary DK/Pikachu qualification remains preserved;
the coordinator will reconcile formerly excluded Final rows after publication.
The runtime owner becomes the exclusive future owner of necessary shared
Character/MatchScene, factory/schema, input/replay, mode and UI integration.
Other agents supply source/art leaves; the coordinator reviews shared changes.

Proposed modules and exact consumers are in `runtime-plan.json#finalSmash` and
`runtime/staged/staging-plan.json`. A deterministic match controller owns
resource readiness, legal activation, consumption, capture links, per-final
phase clocks, damage/protection/release and cleanup. Separate typed leaves hold
the source meter policy, Smash Ball article and each Final's timeline. Ordinary
grab ownership must not be reused blindly for multiplayer cinematic capture;
explicit participant links and reset-generation guards are required.

Activation should use the current special binding if the source confirms that
rule. P1 currently uses G, P2 Numpad2 and standard gamepad profiles button3;
the displayed READY hint must resolve the player's actual saved bindings.
Direction/neutrality, rising edge, action admission and ordinary-special
priority await the source contract. No arbitrary new key or guessed activation
shortcut is planned. UI reads actual readiness/meter, with gameplay clocks in
the controller. CPU uses the same legal input route.

Availability must follow researched meter gains/loss/caps/death carry and Smash
Ball spawn/HP/contact/ownership/consumption rules. Mode/config/menu and Item
Switch persist those choices; compatibility defaults and meter/ball coexistence
remain explicit unresolved decisions. Smash Ball becomes a new catalog/article
entry only when implemented, preserving existing item indices and extending
derived fighter-item inventories. Its movement/spawn randomness uses a private
seeded stream with snapshot/restore; it is not an ordinary holdable weapon.

Existing replay special input can carry activation if source conditions confirm
that binding. Match rules, engine identity and complete runtime resource/capture/
phase state must survive replay and snapshot resync. Any necessary new input
action requires explicit replay versioning. Fighter saves hold source Final
definitions/version; match-only readiness is not permanent character data.
Legacy saved tunes and old replay readability remain distinct from updated
BASE gameplay.

Source contracts must cover hit/whiff/multiple targets, simultaneous activation,
cinematic versus world clocks, ordinary projectiles/items/traps, protection,
held equipment, camera, hitlag/pause, disconnect, KO/stock/respawn, match-end and
teardown. There is no assumed global freeze, forced item loss, target cap,
damage formula or final instant-KO rule. Unknown fields remain source gaps.
Executable staged drafts wait for resolved contracts; the staging directory
currently contains planning only. No compiled-tree mutation occurs before
the current DK/Pikachu publication, and no checks run until the complete end
verification of Link plus all three Finals/shared-system behavior.
